# Release v0.12.0 - Dispute Resolution System

**Release Date:** November 22, 2025
**Type:** Minor Release (New Feature)
**Tests:** 467 passing (+33)

## 🚀 Major Features

### Dispute Resolution System with Admin Intervention

A comprehensive dispute resolution system that allows users to report issues with trades and enables admins to review and resolve conflicts with full audit trails.

## ✨ New Features

### 1. Trade Dispute Management

- **File Disputes**: Users can file disputes against their trade partners
- **Dispute Reasons**: 6 predefined dispute types for better categorization
- **Automatic Validation**: System ensures users are part of the trade before allowing disputes
- **Duplicate Prevention**: Users cannot file multiple disputes for the same trade

### 2. Admin Dispute Workflow

- **Assignment System**: Admins can assign disputes to themselves for review
- **Status Tracking**: Clear workflow states (OPEN → UNDER_REVIEW → RESOLVED/CLOSED)
- **Resolution Notes**: Admins can add detailed notes and resolutions
- **Trade Cancellation**: Resolving disputes automatically cancels the associated trade

### 3. Role-Based Access Control

- **Admin Guard**: New guard for protecting admin-only endpoints
- **User Admin Flag**: Added `isAdmin` field to User model
- **Access Control**: Users can only view their own disputes unless they're admins

### 4. Comprehensive Dispute Endpoints

- `POST /disputes` - Create a new dispute (user)
- `GET /disputes/my` - Get user's disputes (user)
- `GET /disputes/:id` - Get specific dispute (user/admin)
- `GET /disputes?status=` - Get all disputes with filtering (admin only)
- `PATCH /disputes/:id/assign` - Assign to admin (admin only)
- `PATCH /disputes/:id/resolve` - Resolve with notes (admin only)
- `PATCH /disputes/:id/close` - Close without resolution (admin only)

## 📊 Database Changes

### New Models

- **Dispute** model with comprehensive tracking
- **DisputeStatus** enum: OPEN, UNDER_REVIEW, RESOLVED, CLOSED
- **DisputeReason** enum: 6 dispute types including ITEM_NOT_AS_DESCRIBED, SCAM_ATTEMPT, etc.

### Schema Updates

- Added `isAdmin` Boolean field to User model
- Added dispute relations to User and Trade models
- Migration: `20251122151635_add_dispute_resolution_system`

## 🔧 Technical Implementation

### Services

- **DisputesService**: 8 methods for complete dispute lifecycle management
  - `createDispute()`: Validates trade participation and creates disputes
  - `getUserDisputes()`: Returns disputes for/against a user
  - `getDispute()`: Access-controlled dispute retrieval
  - `getAllDisputes()`: Admin-only with optional filtering
  - `assignDispute()`: Assigns dispute to admin
  - `resolveDispute()`: Resolves with notes and cancels trade
  - `closeDispute()`: Closes without resolution
  - `formatDisputeResponse()`: Consistent response formatting

### Controllers

- **DisputesController**: 7 REST endpoints with full Swagger documentation
  - 3 user-accessible endpoints
  - 4 admin-only endpoints with AdminGuard protection

### Guards

- **AdminGuard**: Database-based role verification
  - Checks `user.isAdmin` field
  - Throws `ForbiddenException` for unauthorized access

### DTOs

- **CreateDisputeDto**: Dispute creation with validation
- **ResolveDisputeDto**: Admin resolution data
- **DisputeResponseDto**: Standardized response format with 16 fields

## 🔒 Security & Validation

### Business Rules

1. Users must be part of a trade to file disputes
2. Users cannot dispute themselves
3. Users cannot file duplicate disputes for the same trade
4. Only trade participants and admins can view disputes
5. Only admins can assign, resolve, or close disputes

### Validation

- All DTOs use class-validator decorators
- Trade existence and participation verified
- Reported user existence validated
- Access control enforced at multiple levels

## 📝 API Documentation

### User Endpoints

```http
POST /disputes
Body: {
  "tradeId": "string",
  "reportedUserId": "string",
  "reason": "ITEM_NOT_AS_DESCRIBED | SCAM_ATTEMPT | ...",
  "description": "string (max 2000 chars)"
}
Response: DisputeResponseDto

GET /disputes/my
Response: DisputeResponseDto[]

GET /disputes/:id
Response: DisputeResponseDto
```

### Admin Endpoints

```http
GET /disputes?status=OPEN
Response: DisputeResponseDto[]

PATCH /disputes/:id/assign
Response: DisputeResponseDto (status → UNDER_REVIEW)

PATCH /disputes/:id/resolve
Body: {
  "adminNotes": "string (10-2000 chars)",
  "resolution": "string (10-2000 chars)"
}
Response: DisputeResponseDto (status → RESOLVED, trade cancelled)

PATCH /disputes/:id/close
Response: DisputeResponseDto (status → CLOSED)
```

### Dispute Response Format

```typescript
{
  id: string;
  tradeId: string;
  reporterId: string;
  reporterUsername: string;
  reportedUserId: string;
  reportedUserUsername: string;
  reason: DisputeReason;
  description: string;
  status: DisputeStatus;
  adminId: string | null;
  adminUsername: string | null;
  adminNotes: string | null;
  resolution: string | null;
  resolvedAt: Date | null;
  createdAt: Date;
  updatedAt: Date;
}
```

## 🔄 Migration Guide

### Database Migration

```bash
# Run migration to add dispute system
yarn prisma migrate deploy

# Or for development with reset
yarn prisma migrate dev
```

### Admin User Setup

```sql
-- Grant admin privileges to a user
UPDATE "User" SET "isAdmin" = true WHERE id = 'user-id';
```

### API Integration

All endpoints require JWT authentication. Admin endpoints additionally require the `isAdmin` flag to be true in the database.
