# Release v1.5.0 - Admin & User Authentication Split

**Release Date**: December 26, 2025
**Version**: 1.5.0
**Release Type**: Feature Release

## 🎯 Overview

This release implements a complete separation of admin users and regular users into distinct database tables with dedicated authentication systems. Admin users (ADMIN, MODERATOR, SUPPORT roles) now authenticate through a separate endpoint and are managed in the `admin_users` table, while regular users remain in the `users` table. This architectural change enhances security, improves scalability, and provides better role-based access control for administrative operations.

## ✨ New Features

### Dual Authentication System

- **Separate Admin Authentication**: New `/api/admin/auth/*` endpoints for admin user login and management
- **AdminUser Table**: Dedicated table for admin users with role-based access control
- **Admin MFA Support**: Multi-factor authentication specifically for admin accounts
- **Enhanced Security**: Admin tokens cannot access user endpoints and vice versa
- **Admin Profile Management**: Dedicated admin profile endpoints with role verification

### Guard System Refactor

- **AdminJwtAuthGuard**: New guard specifically for admin user authentication
- **AdminRoleGuard**: Role-based guard for ADMIN/MODERATOR/SUPPORT differentiation
- **Guard Separation**: Eliminated guard stacking conflicts between User and AdminUser authentication
- **Explicit Guards**: Each endpoint now has clear guard declarations (no class-level ambiguity)

### Database Architecture

- **AdminUser Model**: Separate table with fields optimized for administrative users
- **AdminMfaSecret Model**: MFA secrets table specific to admin users
- **Data Migration**: Automatic migration of existing admin users to new table structure
- **Rollback Support**: Comprehensive rollback SQL for safe migration reversal

### Database Migrations

**Migration: 20251221063004_split_admin_user_tables** (147 lines)

```prisma
// New enum for admin roles
enum AdminRole {
  SUPPORT
  MODERATOR
  ADMIN
}

// New admin users table
model AdminUser {
  id            String      @id @default(cuid())
  email         String      @unique
  username      String      @unique
  password      String
  avatarUrl     String?
  role          AdminRole   @default(SUPPORT)
  createdAt     DateTime    @default(now())
  updatedAt     DateTime    @updatedAt
  lastLoginAt   DateTime?
  isActive      Boolean     @default(true)
  mfaEnabled    Boolean     @default(false)
  createdBy     String?     // Reference to admin who created this admin

  // Relations
  mfaSecret     AdminMfaSecret?
  performedAudits AuditLog[]
  resolvedDisputes Dispute[]
  reviewedItems   FlaggedItem[]
  reviewedComments FlaggedComment[]
  supportChats    SupportChat[]
  adminMessages   SupportMessage[]

  @@index([email])
  @@index([username])
  @@index([role])
  @@map("admin_users")
}

// Admin MFA secrets
model AdminMfaSecret {
  id          String    @id @default(cuid())
  adminUserId String    @unique
  secret      String
  createdAt   DateTime  @default(now())
  adminUser   AdminUser @relation(fields: [adminUserId], references: [id], onDelete: Cascade)

  @@map("admin_mfa_secrets")
}

// Updated SupportMessage model
model SupportMessage {
  // Split sender into user and admin
  userSenderId  String?
  adminSenderId String?
  userSender    User?      @relation(fields: [userSenderId], references: [id])
  adminSender   AdminUser? @relation(fields: [adminSenderId], references: [id])
}
```

## 📝 Business Rules

### Authentication & Authorization

- ✅ Admin users must authenticate via `/api/admin/auth/login`
- ✅ Regular users must authenticate via `/api/auth/login`
- ✅ Admin JWT tokens contain AdminUser data and role information
- ✅ User JWT tokens contain User data (no role field)
- ✅ Admin tokens cannot access user-only endpoints
- ✅ User tokens cannot access admin endpoints
- ✅ Only ADMIN role can create new admin users
- ✅ SUPPORT role can access support endpoints only
- ✅ MODERATOR role can access moderation endpoints
- ✅ ADMIN role has access to all admin endpoints

### Guard Stacking Rules

- ✅ Each endpoint must have explicit @UseGuards decorator
- ✅ Cannot mix JwtAuthGuard and AdminJwtAuthGuard on same endpoint
- ✅ Class-level guards removed to prevent stacking conflicts
- ✅ AdminRoleGuard must always be paired with AdminJwtAuthGuard
- ✅ VerifiedGuard only works with JwtAuthGuard (user authentication)

### Data Migration

- ✅ Existing admin users automatically migrated to admin_users table
- ✅ Old admin user data deleted from users table after migration
- ✅ Support message sender references split into user/admin fields
- ✅ Foreign key constraints updated to point to correct tables
- ✅ Rollback SQL provided for safe migration reversal

## 🔄 Migration Notes

### Automatic Migration

The migration runs automatically when deploying. It will:

1. Create `AdminRole` enum and `admin_users` table
2. Migrate existing admin users from `users` to `admin_users`
3. Update all foreign key constraints
4. Split `support_messages.senderId` into `userSenderId` and `adminSenderId`
5. Delete migrated admin users from `users` table

### Manual Rollback (if needed)

```bash
# Generate rollback SQL
yarn migrate:gen-rollback:all

# Execute rollback for specific migration
yarn migrate:rollback 20251221063004_split_admin_user_tables

# Or rollback last migration
yarn migrate:rollback:last
```

### Post-Migration Verification

```bash
# Check admin users were migrated
psql $DATABASE_URL -c "SELECT COUNT(*) FROM admin_users;"

# Verify no admin users remain in users table
psql $DATABASE_URL -c "SELECT COUNT(*) FROM users WHERE role IN ('ADMIN', 'MODERATOR', 'SUPPORT');"

# Should return 0
```

## 🔄 Breaking Changes

### API Changes

⚠️ **Admin endpoints now require different authentication**:

- Old: `Authorization: Bearer <user_jwt_token>` (admin role required)
- New: `Authorization: Bearer <admin_jwt_token>` (from `/api/admin/auth/login`)

### Affected Endpoints

All endpoints under:

- `/api/admin/*` - Admin operations
- `/api/disputes` (admin endpoints) - Dispute resolution
- `/api/verification/admin/*` - Verification review
- `/api/support/agent/*` - Support agent operations
- `/api/moderation/*` - Content moderation

### Migration Guide for Clients

```javascript
// Before (v1.4.0)
const response = await fetch('/api/admin/stats', {
  headers: { Authorization: `Bearer ${userToken}` },
});

// After (v1.5.0)
// Step 1: Login as admin
const adminAuth = await fetch('/api/admin/auth/login', {
  method: 'POST',
  body: JSON.stringify({
    email: 'admin@swapbuds.com',
    password: 'Password123!',
  }),
});
const { accessToken: adminToken } = await adminAuth.json();

// Step 2: Use admin token
const response = await fetch('/api/admin/stats', {
  headers: { Authorization: `Bearer ${adminToken}` },
});
```

## 📝 Notes

### Why This Change?

1. **Security**: Isolates admin credentials from user credentials
2. **Scalability**: Admin operations don't impact user table performance
3. **Compliance**: Better audit trail separation for GDPR/regulatory requirements
4. **Flexibility**: Different authentication policies for admin vs users (e.g., stricter MFA requirements)

### Future Enhancements (Post-Launch)

- Admin session timeout configuration separate from users
- Admin IP whitelisting for enhanced security
- Admin action replay/undo functionality
- Enhanced audit logging with admin action categorization
- Admin notification system separate from user notifications

### Known Limitations

- Frontend admin dashboard needs update to use new authentication
- Admin users cannot have items, trades, or engage in user activities
- Migration is one-way (rollback available but data may be lost)
