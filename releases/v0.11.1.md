# Release v0.11.1 - Trade Expiration System

**Release Date**: November 22, 2024
**Version**: 0.11.1
**Release Type**: Patch Release

## Overview

Automatic trade expiration system that ensures pending trade proposals don't remain open indefinitely. Trades expire after 72 hours with warning notifications sent 24 hours before expiration.

## Features

### Automatic Trade Expiration

- **Configurable Expiration**: Trades expire after 72 hours (configurable via environment variables)
- **Warning System**: Responders receive notifications 24 hours before expiration
- **Automatic Status Update**: Trades automatically transition to EXPIRED status
- **Scheduled Jobs**: Cron jobs run hourly (expiration check) and every 6 hours (warnings)
- **Email Notifications**: Both in-app and email notifications for expiration events

### Expiration Configuration

- Default expiration: 72 hours after trade creation
- Default warning: 24 hours before expiration
- Customizable via `TRADE_EXPIRATION_HOURS` and `TRADE_EXPIRATION_NOTIFICATION_HOURS`

### Email Templates

- `trade-expired.hbs` - Expiration notification
- `trade-expiring.hbs` - 24-hour warning

## API Endpoints

All existing trade endpoints now include `expiresAt` field in responses:

```json
{
  "id": "trade-123",
  "status": "PENDING",
  "expiresAt": "2024-11-25T10:30:00.000Z"
}
```

No new endpoints added - backward compatible enhancement.

## Technical Implementation

### New Components

- **TradeExpirationService**: Core service handling expiration logic
  - `@Cron(EVERY_HOUR)` for expiration checks
  - `@Cron(EVERY_6_HOURS)` for warning notifications
  - `calculateExpirationDate()` for new trades
- **MailService Methods**:
  - `sendTradeExpired()` - Notify both parties of expiration
  - `sendTradeExpiringWarning()` - 24h warning to responder

### Dependencies

- Added `@nestjs/schedule@6.0.1` for cron job scheduling
- Integrated ScheduleModule in AppModule

### Service Integration

- TradesService sets `expiresAt` on trade creation
- Uses `forwardRef` to handle circular dependency
- TradeResponseDto includes new `expiresAt` field

## Business Rules

- ✅ Trades expire 72 hours after creation (configurable)
- ✅ Warning sent to responder 24 hours before expiration
- ✅ Only PENDING trades can expire
- ✅ Accepted/rejected/cancelled trades ignore expiration
- ✅ Both parties notified when trade expires
- ✅ Expired trades have status EXPIRED
- ✅ All dates stored in UTC

3. Restart application

- **Efficient queries**: Uses indexed fields (status, expiresAt)
- **Non-blocking**: Async notification and email sending
- **Cron Schedule**:
  - Expiration check: Every hour at minute 0
  - Warning check: Every 6 hours at minute 0

## Notes

- Existing trades created before this release will not have `expiresAt` (null value)
- Frontend should handle null `expiresAt` gracefully
- Trade expiration helps keep platform active with timely responses
- Email notifications improve user engagement and response rates
- System catches up on missed expirations if server was down
